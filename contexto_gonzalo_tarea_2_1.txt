2. LA CI AHORA CORRE DENTRO DE DOCKER (y por que)
------------------------------------------------------------------------

Antes la CI instalaba requirements-qkd.txt (un subconjunto minimo) en el
runner de GitHub para no tener que compilar liboqs. Con el modulo 2 eso ya no
vale: liboqs es una libreria en C SIN wheel, hay que COMPILARLA. Replicar ese
build en el runner duplicaria la logica del Dockerfile y acabaria divergiendo.

Asi que la CI ahora hace `docker build -t qpcs:ci .` y corre ruff/black/mypy/
pytest con `docker run` sobre esa imagen. El Dockerfile ya es "la fuente de
verdad" del proyecto ("si funciona en Docker, funciona") e instala
requirements.txt + requirements-dev.txt completos (liboqs-python, cryptography,
qiskit, ruff/black/mypy...). Por eso desaparece requirements-qkd.txt.

Para ti esto significa: si tu codigo/tests pasan con
  docker run --rm qpcs:ci pytest tests/ -m "not slow"
pasan en CI. No dependas del venv local para dar algo por bueno.

4. EL CONTRATO QUE DEBE DEVOLVER factorizar_15
------------------------------------------------------------------------

En src/pqc/types.py (NO lo cambies sin avisar):

    @dataclass(frozen=True)
    class FactorizacionShor:
        n: int                      # el N factorizado
        factores: tuple[int, int]   # (p, q) con p*q == N (o (1, N) si fracasa)
        a: int                      # la base que funciono (o la ultima probada)
        orden: int                  # el orden r hallado
        intentos: int               # cuantas iteraciones costo
        fase_medida: float          # la fase de la iteracion con exito
        ok: bool                    # True si p*q == N con p,q no triviales

Es un dataclass frozen: se construye una vez y no se muta. Devuelve SIEMPRE una
instancia (tambien en el caso de fracaso, con ok=False y factores=(1, N)), no
None: asi el dashboard y los tests pueden inspeccionar por que fallo.

6. NOTA sobre nomenclatura liboqs (para el review de todos)
------------------------------------------------------------------------

Al montar el test de mecanismos comprobe algo que conviene que sepa el equipo:
liboqs 0.14.0 (la que compila nuestro Dockerfile) SIGUE exponiendo los nombres
pre-estandarizacion "Kyber768" y "Dilithium3" como ALIAS, conviviendo con los
nombres NIST "ML-KEM-768"/"ML-DSA-65". O sea: liboqs NO nos obliga a usar la
nomenclatura correcta. Que en nuestro codigo aparezca solo ML-KEM-*/ML-DSA-*
(FIPS 203/204) y nunca Kyber/Dilithium (salvo como nota historica puntual) es
una regla de REVIEW, no algo que un test pueda derivar de liboqs. El test de
test_scaffold.py comprueba que los nombres NIST estan presentes y lo documenta
en un comentario. No afecta a tu parte (Shor no usa liboqs), pero por si lo ves
en el review.
